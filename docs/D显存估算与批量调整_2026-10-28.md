# D正式训练：显存估算与后续batch调整

日期：2026-10-28。本轮只做源码／架构估算和显存日志补充，没有访问用户Windows显卡、运行真实CUDA探测或调整正在训练的batch。当前Windows显卡及实测占用待用户提供。

## 1. 估算前提与已有记录

对象为`D.unpaired`正式无配对训练，不是`D.preview`或RGB自配对预热：360×288、batch1、CFG1、10个DDIM总时间步×strength0.4＝实际4步、完整采样链反传、梯度检查点、混合精度、双循环依次反传、RGB回放每4次更新一次、RGB教师默认GPU／语义损失256。FMB重算合成TIR条件默认CPU。

仓库README记录过RTX3070Ti Laptop 8GB短测4次更新（包含一次回放）的张量峰值约5.53GiB。原始JSON／run没有同步本机，因此是**已有文档记录，非本轮复测、非当前Windows读数，也不是长期上界**。之前日志格式演示的5.53只是沿用了这个示例，不能作为新测量。

## 2. 固定开销的架构估算

使用Torch2.6.0、Diffusers0.32.2在meta／空权重设备上构造网络，统计参数形状与源码中的dtype，不下载权重、不执行图像前向。SD架构参考官方[UNet配置](https://huggingface.co/stable-diffusion-v1-5/stable-diffusion-v1-5/blob/main/unet/config.json)、[VAE配置](https://huggingface.co/stable-diffusion-v1-5/stable-diffusion-v1-5/blob/main/vae/config.json)，ControlNet参考项目[固定commit配置](https://huggingface.co/lllyasviel/control_v11p_sd15_canny/blob/115a470d547982438f70198e353a921996e2e819/config.json)，RGB教师参考[NVIDIA配置](https://huggingface.co/nvidia/segformer-b2-finetuned-cityscapes-1024-1024/blob/main/config.json)。本轮无法打开项目固定SD／教师commit的配置页面，因此没有宣称逐一核对当前本地权重；参数大小按标准相同架构估算。

| 项目 | 参数权重约占GiB | 说明 |
|---|---:|---|
| SD UNet＋rank4交叉注意力LoRA | 1.60 | 冻结主干FP16，LoRA FP32 |
| ControlNet | 0.70 | 冻结主干FP16，条件编码／投影FP32 |
| VAE | 0.16 | FP16、冻结参数，生成路径仍需传图像梯度 |
| RGB SegFormer-B2教师 | 0.10 | FP32、冻结参数，生成路径可微 |
| 反向网络＋两域判别器 | 0.063 | FP32训练 |
| 源内容＋语义／颜色适配器 | 0.0016 | 颜色特征按9个GMM分量、45通道示例 |
| **权重合计** | **2.62** | 不等于整个训练显存 |
| 两个优化器的Adam一／二阶状态 | **0.23** | 稳定训练后建立，不包括临时工作区 |
| 全部可训练参数梯度上界 | **0.11** | 计算相位不同，未必同时存在 |

权重＋优化器状态约2.85GiB；把全部参数梯度一起计入约2.96GiB。没有另加一套假想的FP32主权重：本实现可训练权重本身已是FP32。扩散部分可训练参数约1341万，与仓库记录量级一致。

[逐项计算JSON](../runs/D/review_20261028/static_memory.json)和[估算脚本](../runs/D/review_20261028/static_memory.py)为本地辅助产物，不是CUDA profiler输出。未计入：激活／反向保存张量、缓冲、AMP临时转换、CUDA算子工作区、分配器缓存、驱动／桌面及其他进程。文本编码器只在初始化编码文本后留CPU，不作为常驻GPU模型；默认CPU的FMB也不计入GPU固定权重。

因此主要增长项是中间特征与计算图，不能用“可训练1341万参数”推导整个模型只占很小显存，也不能把全部显存直接乘batch倍数。

## 3. batch1／2／4的规划范围

近似模型为：

\[
M(B)\approx M_{\mathrm{fixed}}+B\,M_{\mathrm{activation}}.
\]

已知文档单点5.53GiB不足以辨识两项。用约3—4GiB作为含部分工作区的固定量级，其余约1.5—2.5GiB作为batch1可增长部分，外加算子选择的不确定性，得到以下**粗略规划范围**：

| batch | 训练张量峰值粗估 | 对实际GPU容量的含义 |
|---|---:|---|
| 1 | 约5—6GiB | 文档锚点为5.53；实际仍依配置／后端变化 |
| 2 | 约7—9GiB | 8GB不能预先保证容纳；12GB值得作为下一档实测 |
| 4 | 约11—15GiB | 12GB不宜直接作为默认；16GB仍需验证额外占用 |

这些范围不含完整缓存／驱动／桌面／其他任务，也不是置信区间或OOM保证。V2没有增加网络容量，预计与V1同一量级，掩膜和临时张量仍有额外成本，不能直接承诺峰值相等。

分辨率、实际反传的去噪步数、教师输入尺度、CFG、是否启用检查点、精度及后端同时改变时，表中范围不再适用。两侧循环虽分图反传，共享模型权重并一直保留累积梯度，不能按两个完整模型峰值简单相加。

## 4. 新显存日志及含义

沿用PyTorch2.6[显存管理定义](https://docs.pytorch.org/docs/2.6/notes/cuda.html#memory-management)，在原日志周期记录：

| JSONL字段 | 含义 |
|---|---|
| `allocated_gib` | 日志时刻，本进程PyTorch张量已分配量；在更新结束、梯度清理后采样，通常低于训练峰值 |
| `reserved_gib` | 当时本进程PyTorch分配器保留量，包含已分配张量和未使用缓存 |
| `peak_allocated_gib` | 自当前进程启动／上次reset以来的张量峰值，沿用原字段 |
| `peak_reserved_gib` | 对应分配器保留峰值 |
| `device_free_gib` | `cudaMemGetInfo`在采样时刻报告的整卡剩余量，会受桌面和其他进程影响；不是整个更新期间的最小剩余量 |
| `device_total_gib` | 同一接口报告的设备总显存 |

终端仍保留三行，用`VRAM peak/resv/free=5.53/6.1/1.3GiB`紧凑显示。示例数字不是实测。`reserved`已包含`allocated`，**不能把两者相加**；当前free与历史peak不发生在同一时刻，也不能直接相加推算可用batch。

本轮没有加每步`empty_cache()`、改变分配器或关闭梯度。日志是轻量读数，不为测内存改变训练路线。仅有更新结束的free采样仍可能漏掉瞬时低谷；判断上限需要后续完整更新的峰值与整卡监控。

当前Windows进程仍使用原代码，可以在另一个终端只读监控，无需启动另一个模型：

```powershell
nvidia-smi --query-gpu=name,memory.total,memory.used,memory.free,utilization.gpu --format=csv -l 1
```

这不是PyTorch张量峰值，1秒采样也可能漏瞬时峰值。把显卡型号／容量、运行配置、日志中的`peak_allocated_gib`与上述读数一起记录，才能缩小估算范围。

## 5. 后续正式调整方法

1. 当前训练先完成，保存配置及峰值记录。现有正式加载器仍每次读取1张，尚无有效`--batch-size`入口，本轮没有假装通过改字段实现batch训练。
2. 后续实现真正batch时，还要处理两域独立取样／拼接、历史池按图或按batch的容量定义、损失归一化、配置签名及恢复状态。已修复逐图合成条件和内容mask，但不是完整批量训练支持。
3. 固定尺寸、模型、精度、损失和数据，用独立短测分别测batch1与2，至少先预热，再测几十次完整更新；覆盖RGB回放、优化器状态建立、保存和预览。记录张量／保留峰值、整卡占用及`TIR images/s=batch÷每更新秒数`，再决定是否测4。
4. 保留约10%—20%的实际显存余量作为工程目标，不把显卡刚好塞满当成成功；比例不是通用安全保证。
5. 改batch后，相同更新数会看到更多图像，颜色预热／学习率日程按步数的含义也变化。做性能对照要同时报告样本预算、更新预算和时间，不自动按比例提高学习率。
6. 梯度累积可增加有效batch并控制单次峰值，但通常不带来真正batch并行的同等吞吐收益；GAN更新和回放周期也要相应定义。先看当前瓶颈是否在GPU，若合成TIR的CPU语义推理主导，增大batch未必明显提速。
